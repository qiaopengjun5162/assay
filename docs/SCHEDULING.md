# 接调度：让体检站在日报发送之前说话

> **状态**：脚本和门禁已写好、CI 三档冒烟通过；**生产 cron 尚未挂**。
> 本会话没有生产服务器权限，第四节是给能登录 Hermes 的同事的操作单。
> 先空跑观察，再真的拦截发报——别把「门禁上线」和「改了日报链路」当成一件事。

## 一句话讲清这是个什么东西

给非技术同事的描述：

> 以前是每天到点就把新闻发出去，发完才发现里面混了一年前的旧闻、或者多数条目只有标题。
> 现在在发送前加一道安检：先给素材做体检，体检不过就先拦下来、叫人看一眼。
> 安检只管「这批数据可不可信」，不管「新闻写得好不好」。

## 一、现在卡在哪、谁做什么

| 角色 | 做什么 | 已经做了吗 |
|---|---|---|

本会话**不碰生产服务器、不改 qunmind 配置、不碰密钥**。下面所有命令都是给同事在自己的登录会话里跑的。

## 二、门禁三档：它到底怎么决定

门禁只读两个文件：`out-news/summary.json`（体检汇总）和 `out-news/run.json`（这轮跑批的口径与时间）。
它不读新闻正文，也不评真假。

| 退出码 | 屏幕上的字 | 人话 | 条件（任一命中） | 动作 |
|---|---|---|---|---|
| `0` | `GATE=PASS` | 可发 | 条目够、抓取成功率够、结构没变、旧闻占比不超标 | 日报照常推送 |
| `1` | `GATE=BLOCK` | 先别发 | 一致性错位 > 0，或超 90 天占比 > 20% | 跳过本次推送，通知人确认 |
| `2` | `GATE=UNTRUSTED` | 这趟车本身坏了 | 条目 < 10、抓取成功率 < 90%、产物超过 26 小时、文件读不到 | 跳过推送并报警（不是「素材差」，是「体检没做成」） |

**「说明不足」故意不拦。** 真实数据 59 条里有 49 条只有标题、没有摘要，占八成多。
拿它当门禁等于天天不发报。它只在放行时打一行「提醒：N 条说明不足」给编辑看。

这个三档设计和周度巡检一致（见 `docs/audit/README.md`）：先把「跑批可不可信」判掉，
再谈「指标漂没漂」。顺序反了，脏数据会进对照系，之后所有对比都不可信。

## 三、阈值从哪来：都是经验值，必须校准

| 环境变量 | 默认 | 依据 | 什么时候调 |
|---|---|---|---|
| `GATE_MIN_ITEMS` | `10` | 2026-11-26 真实导出 59 条；低于 10 基本等于上游没启用或导出空数组 | 来源增删后 |
| `GATE_MIN_FETCH_RATE` | `0.9` | 抓取成功率塌方通常意味着接口改版或代理挂了 | 连续误判不可信时 |
| `GATE_MAX_MISMATCH` | `0` | 结构错位一次都不该有：#77 修正后 59 条真实数据 `schemaMismatch=0` | 上游改字段且确认合法后 |
| `GATE_MAX_LAG_RATIO` | `0.2` | 真实数据 1/59 ≈ 1.7%；20% 是留了十倍余量 | 连续一周误拦时收紧/放宽 |
| `GATE_MAX_AGE_HOURS` | `26` | 日报每天 08:00；跨一天多一点还算当天结果，再旧就是上次跑批残留 | 改推送时间时 |

**这些不是 `checks.rs` 里的检查项阈值。** 那边决定「这条数据算不算有问题」，
这里决定「今天这批改没问题就别发」。两套数不能混，混了就会出现「检查通过但天天拦截」。

校准办法：连续空跑 7 天，记下每天的 `GATE=PASS/BLOCK/UNTRUSTED`。
一周里误拦超过 1 次才调阈值，按观测到的 P95 再留一倍余量；不要看到一次拦截就放宽。

## 四、挂到 cron（同事执行；本会话不碰生产）

### 4.1 先确认现有日报的定时器在哪

别急着加 cron——同一个日报挂两遍会发两篇。先看现有链路是哪种：

```bash
# A. Hermes cron（本机 Hermes 服务）
hermes cron list 2>/dev/null | grep -i '日报\|report'

# B. qunmind 自己的调度配置
grep -n -A5 'daily_reports' /path/to/qunmind/config.toml

# C. systemd timer（服务器上）
systemctl list-timers | grep -i 'qunmind\|report'
```

三处最多只能有一处在发日报。门禁是**旁路**，只加一道检查，不新起一个发报任务。

### 4.2 本地先验收（同事在服务器上先跑一次，别直接上 cron）

```bash
cd /path/to/assay

QUNMIND_BIN=/path/to/qunmind/target/release/qunmind \
QUNMIND_CONFIG=/path/to/qunmind/config.toml \
bash scripts/news-check.sh --export --gate -o out-news
```

看到 `GATE=PASS` 才算验收通过。若看到 `GATE=UNTRUSTED`，先看提示里的具体原因：
「条目只有 0 条」多半是 `config.toml` 里没有启用任何 `public_sources`；
「产物过期」说明导出那步没跑成功，读到了上次的旧文件。

### 4.3 挂上去（建议 07:55，日报 08:00 前 5 分钟）

```bash
55 7 * * * cd /path/to/assay && \
  QUNMIND_BIN=/path/to/qunmind/target/release/qunmind \
  QUNMIND_CONFIG=/path/to/qunmind/config.toml \
  bash scripts/news-check.sh --export --gate -o /path/to/assay/out-news \
  >> /var/log/assay-news-gate.log 2>&1
```

cron 拿到退出码后的处理：

| 退出码 | 对日报链路做什么 |
|---|---|
| `0` | 什么都不用做，日报按原节奏发 |
| `1` | 跳过本次推送，把日志最后 20 行发到值班群，请人确认 |
| `2` | 跳过推送并明确报警：「体检没做成」和「素材有问题」是两回事，措辞别混 |

⚠️ 通知那一步要接现有 WeCom 通道（小满/二花已有），本会话不实现也不代配。
在完成通知之前，**先只空跑、不真的拦发报**——拦了却没人知道，比不拦更糟。

### 4.4 通知文本怎么拼（同事执行；本会话不碰通道）

不用再装新脚本：体检摘要和门禁结论 4.3 的日志里已经齐了。cron 每次把输出
**追加**到同一个日志文件，下面这条命令只取**最后一次运行**的整段输出
（每遇到一个新的「公众号日报体检」就丢掉前面所有内容），复制出来贴值班群即可：

```bash
LOG=/var/log/assay-news-gate.log
awk '/公众号日报体检 · /{buf=""} {buf=buf $0 "\n"} END{printf "%s", buf}' "$LOG"
```

贴出来长这样（`GATE=` 那行是关键：`PASS` 不用动，`BLOCK`/`UNTRUSTED` 叫人看一眼）：

```text
公众号日报体检 · 公众号日报（qunmind 条目）
条目 61 条 / 来源 9 个：ArXiv AI(15)、Hacker News(11)…
① 三个数
   说明不足：51 条
   超 90 天未更新：1 条
   一致性错位：0 条
③ 产物
   out-news/items.jsonl / summary.json / checks.txt / leaderboard.md
── 发报门禁 ──────────────────────────────────────────
GATE=PASS
可发报：61 条，抓取成功率 100.0%，一致性错位 0，超 90 天 1.6%。
```

**本会话不做的**：不内置 webhook 地址、不读密钥、不代发消息。发到小满/二花的现有
WeCom 通道，还是先贴值班群人工转，由能登录的同事定。**通知没接好之前只空跑、不真拦**。

### 4.5 观察窗口

1. **第 1 周**：门禁只记日志，不拦发报。每天看 `GATE=` 那一行和条目数。
2. **第 2 周**：确认零误拦后，才把 `1` / `2` 接到「跳过推送」。
3. **上线后**：盯 7 天；出现一次 `UNTRUSTED` 就去查上游，不要直接放宽阈值。

## 六、边界（明确不做的事）

- 不评新闻真假：没有权威源，评了就是编（见 `docs/DECISIONS.md`）。
- 不生成日报正文：门禁只回答「发不发」，写稿仍由 qunmind 日报链路负责。
- 不改生产配置、不读密钥：本会话只交付脚本与操作单。

## 七、真实数据实测（2026-11-26 19:08，本机）

不是 fixture，是用 qunmind 现有配置文件读真实公共源，跑完整条链：

```bash
# 在 assay 根目录；qunmind 二进制来自已合并 export-items 的 origin/main
QUNMIND_BIN=/path/to/qunmind/target/release/qunmind \
QUNMIND_CONFIG=/path/to/qunmind/config.toml \
bash scripts/news-check.sh --export --gate -o out-news-real
```

| 指标 | 实测 | 门禁怎么读 |
|---|---|---|
| 条目 / 来源 | 61 条 / 9 个（ArXiv AI 15、Hacker News 11、GitHub Trending 10、ethresear.ch 10、HN Daily 5…） | 远超 10 条下限 |
| 抓取成功率 | 61/61 = 100% | 不触发「不可信」 |
| 一致性错位 | 0 | 不拦截 |
| 超 90 天 | 1/61 = 1.6% | 低于 20%，放行 |
| 说明不足 | 51/61 = 84% | **提醒但不拦**（见第二节） |
| 门禁结论 | `GATE=PASS`，exit 0 | 可发报 |

**反向验证**：同一批产物不改数据，只把时效阈值收紧到 1%
（`GATE_MAX_LAG_RATIO=0.01`），门禁立刻变成 `GATE=BLOCK`、exit 1，
并指出「超 90 天 1/61 = 1.6%（上限 1%）」。这说明它真的在判数据，
不是对真实批次一律放行。

这次导出用到的 `config.toml` 含凭据，只传路径、未读取或打印内容；
产物落在 `out-news-real/`（被 `.gitignore` 的 `out-*/` 覆盖）。
qunmind 二进制在隔离 worktree 里基于 `origin/main` 构建——主工作区有未提交改动，
不能切分支。
